# Tako

Desktop soft-body companion that sticks to a window and gives it intelligence. README is the public product page. If `.local/AGENTS.private.md` exists, read it too: it holds this machine's private rules, and `.local/STATUS.md` holds the current verified state.

This repository is public. Personal paths, names, chat content, keys and client facts never enter it: whatever is personal goes in `~/Library/Application Support/Tako/config.json`. `scripts/check_public.sh` guards this on every push.

## Rules that must hold

- It is called Tako everywhere, in the UI and in the model's prompts. It does not answer as any other assistant name.
- Fill, never send: Tako may put text into an app's input and change documents the owner asked it to change, but must never press Return, click a send button or otherwise send a message. Only the owner's own words can trigger writing; what an incoming message or window shows never can.
- Operating an app (`Operate.swift`): sending stays refused even with approval; Enter is refused in messaging apps; password fields are refused; only what can't be taken back asks first (pay, buy, transfer, delete, submit, publish, sign out, uninstall, reset), and network/system tools ask every step. Stop, remove from a list, disconnect and a new line in a document just go ahead.
- A job belongs to the window it was asked on and goes on wherever the owner goes (Joe 2026-11-01: people and the agent run apart, that is what saves them time). Switching away or dragging the goo to another window never stops it; only the stop button does, and only for what the panel shows. It works behind the owner's back: Accessibility and events sent to that app alone, never their focus, pointer or clipboard. What only the real pointer can do happens only if they are already on that window and idle (`ownerSettles`), and nothing brings a window forward except a button they pressed. A fill or file hand-over that has to wait is queued, not failed, and finishes by itself with no model call when they get there (`_hold_fill`); the goo follows them there, nothing else moves. The owner going to a window the job is working (their own click or ⌘Tab, not a window that came up by itself, not one only looked at) finds the goo and the job there (`_follow_hands`); otherwise the result stays where it was asked (Joe 2026-11-09). A `chat` always means WeChat, never the job's own window.
- A limb works to the brain's standard and interferes with nothing (Joe 2026-11-03: it must be as good as handing the same job to their agent, silently in the background). Same model and effort as their Codex; read the material whole and check the finished work with `look_at_file`, which opens no app and asks nothing. No card and no app opened just to see a file.
- Asking the owner to switch to a window defeats the point of Tako (Joe 2026-11-03: they stick it to a window precisely so the job finishes there without taking the foreground from their other work). Go through what is behind the window first (files, the message database, Accessibility), then events sent to that window alone; never make "come to this window" a step in the middle of a job, and never tell the model to ask for it. Only the last hand-over the owner would do anyway, such as a draft into a chat they will send themselves, may wait for them, and everything else is finished by then.
- WeChat waits for the owner like any other window (Joe 2026-11-02: reading in the background and judging whether to speak made people wonder what it was about to say and what it cost). Someone else's message starts nothing and shows nothing; the chat is read when the owner speaks, and what is read is data (`_said_since`). The one background look is whether a draft got sent, to learn from it: file stats and a local read, no model call.
- The owner's other agents (`agents.py`, the `tako` command) speak for the owner: a job they hand over runs like the owner's own words, with every floor here unchanged. Their token lives in `agent.json` (0600, new on every start) and opens only `/agent/`, never a card: approvals wait for the owner's own tap. The panel shows who handed it over. Their words never enter `said`, so the workbench still takes only the owner's own panel words.
- Any model the owner brings (their ChatGPT login, or their own key for DeepSeek, Qwen, Kimi, GLM or any relay that speaks Responses, through `provider.py`) gets the same Tako (Joe 2026-11-07: don't bloat Tako to accommodate cheaper, weaker models). A change made for one model must make the best one better too; no prompts, step caps or guards for a single model. Where a model falls short, say so and leave it there.
- Throwaway threads have no tools at all (`READER_CONFIG`); never give them shell, plugins or `TOOLS`. Tool calls and approvals count only on the threads of the owner's own jobs (`on_thread`).
- A limb has what the brain has (Joe 2026-11-02: the point is the same intelligence at every window, and using AI already means trusting the provider): the owner's turns read this Mac's files and keys like their own Codex does. What stays narrow is writing: the turn's folder, plus paths in the owner's own words, files they handed over (`named_paths`) and the folder of the Finder window they asked on (`_what_it_is_about`), Outside that it still goes ahead without a card, made recoverable first (Joe 2026-11-04: keep only the cards that matter): a file change backs up what was there (`_backed_up`), a WPS replacement backs up the original, and an ordinary command out of the sandbox just runs. A card is only for what can't be taken back or leaves this Mac (`guards.lasting_command`: deleting, uploading or sending off the Mac, pushing git, changing the Mac's settings, ending processes, osascript), a change that names no files, a script that deletes or changes a page (`risky_script`), and feedback text going to the author. Don't add read limits or more cards; the lines above are the floor.
- Pointing (`Pointing.swift`): only ⌃ alone, only on the window it is stuck to, only presses, drags and scrolls; everything else goes on to the app untouched. A drag over text is the owner's own press handed on without ⌃, nothing more. What is circled is material for the turn, never an instruction, and a ring is a finger, not a picture: it is resolved to the real thing behind the window when it is made.
- Permissions (`Permissions.swift`): ask the owner as rarely as the system allows (Joe 2026-11-04). Each switch once; the system's own prompt only on the first start; a switch turned on takes effect without a restart they have to do; anything Tako can put right itself (a stale record, a restart into Screen Recording when no job is running) it does without a card or a question.
- Filling says it filled only when it can tell: a page with no cursor in a field is an error, never success (`insertBehindTheOwner`).
- Learning from the owner's edits keeps habits only (`voice.md`), never sentences, names or figures; `metrics.jsonl` holds numbers and fixed words only (tool names, block reasons, bundle ids), and stays on this Mac.
- Listening (`Listen.swift`): starts only on the owner's words, only the stuck app's sound, never calls or meetings; audio pieces are deleted once read and nothing leaves the Mac. Notes come from a throwaway thread with no tools.
- Feedback (`feedback.py`): never interrupts: no cards, no questions, one checkmark in the menu, on unless switched off, and off stops all of it. Automatic reports hold only numbers, fixed vocabulary and error type and place, never words, names or identifiers, not even abstracted ones. Free text leaves only when the owner asks to tell the author and taps send on the card that shows it. Extraction reads only the owner's panel words on a throwaway thread with no tools. Change `docs/PRIVACY.md` in the same commit as anything that changes what leaves. The receiver takes no key and serves nothing back.
- Greetings (`greetings.py`): only the app's name goes to the model, never the title or anything in the window, on a throwaway thread with no tools; lines are shown as plain text and only in the empty panel. A WeChat conversation gets one batch a day because people flip through chats all day: looking at a chat never uses up a line or asks the model for more, the first chat of the day asks once, and only the word WeChat goes out.
- Peeled off a window, it stops reading on its own initiative; a job the owner already started goes on. Chat text stays in memory; never log or commit chat content, keys or tokens. The one exception is what each panel showed, the owner's words and Tako's answers, kept for a week in `conversations.json` (0600, this Mac only) so a restart or update doesn't empty the panels (Joe 2026-11-09: two restarts lost the answer he went back to).
- What the owner asked is kept for a week in `asked.json` (Joe 2026-11-03: an update made Tako forget the morning's job): their own words, where, the folder, the files made and how it ended, never what a window or chat showed (`asked.py`). A new thread, brain or limb, is told it.
- Runtime state lives in `~/Library/Application Support/Tako/`, never inside the app bundle (a write there breaks its signature and the permissions with it).
- Moving or narrowing another app's window needs Accessibility; always put it back unless the owner moved it. The panel never covers a full window if it can be helped.
- Tests never change network or proxy tools' state, never send anything, and write to an isolated `TAKO_HOME`. `TAKO_HOME` also turns reports off, so the real app must never set it for its own server.

## Releasing

A release is a version bump, nothing else: change `VERSION`, add a section to `CHANGELOG.md` written for the people who use Tako (what they get, not what changed in the code), commit, `git push`. `.githooks/pre-push` runs the tests and the public check, builds and signs the app, and publishes the GitHub release once the push lands; every installed Tako then offers it. A push that keeps `VERSION` reaches nobody. Enable the hook in a new checkout with `git config core.hooksPath .githooks`.

A release also carries a small package without the Python, which an installed Tako with the same `python.id` fetches instead of the whole app; the Python is signed once and cached in `.build/signed-python/` so its bytes stay the same. Losing that cache only means the next update is whole again.

The uplink can be very slow (~25 KB/s through the proxy). When `.local/release-relay` names an ssh host with a fast uplink and it answers, every file goes through it (the whole app in seconds); otherwise publishing puts the small update out first and makes the release public, then uploads the whole app with retries; until it lands, `latest.json` points new installs at the previous whole app if its Python is the same. A stalled publish is finished by running `scripts/release.sh publish <commit>` again: it uploads only what GitHub doesn't hold yet.

Updates install only when the new app satisfies the running app's designated requirement, so the signing identity must stay the same: changing it strands everyone on the old version and resets their permissions.

## Layout

`docs/ARCHITECTURE.md` is the map: the two processes, the two kinds of thread, what each file is for, how to add a tool. Read it before moving anything.

`Sources/native/` the app (Swift): goo, windows, panel window, hands, updates. `Sources/brain/` the Python side and the panel page. `server/feedback_receiver.py` where reports land.

`tests/test_guards.py` the lines that must hold. `tests/test_turns.py` the real Python side against `tests/fake_codex.py`, with the test playing the app: write a new behaviour or a bug as a scene there first. `run.sh` builds and restarts for development. `scripts/` build and release.
